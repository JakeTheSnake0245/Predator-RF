Perform a full, adversarial code review of this entire project. Do not skim — 
go file by file. Your goal is to find every current bug and every latent/potential 
failure mode, then harden the code. Do not just patch the first issue you find and 
stop; keep going until you've covered every file.

## Scope — check for ALL of the following:

**Correctness**
- Logic errors, off-by-one errors, incorrect conditionals
- Unhandled edge cases (empty inputs, None/null, zero, negative numbers, huge inputs)
- Race conditions / concurrency bugs (async tasks, shared state, threading)
- Incorrect error handling (bare except/catch, swallowed exceptions, wrong exception types)
- Resource leaks (unclosed files, sockets, DB connections, subprocess handles)
- Type mismatches and implicit coercion bugs

**Security**
- Injection risks (SQL, command, path traversal)
- Missing input validation/sanitization on any external input (API params, file uploads, serial/network data)
- Hardcoded secrets, API keys, or credentials
- Insecure deserialization
- Missing auth checks on API endpoints
- Unsafe use of eval/exec/pickle/subprocess with shell=True

**Reliability / production-readiness**
- Missing timeouts on network/serial/API calls
- No retry/backoff logic where it matters
- Silent failures (functions that fail without logging or raising)
- Missing input bounds checks (buffer sizes, array indices, packet lengths)
- Dependency version pinning issues or known-vulnerable packages
- Config/env var handling — missing defaults, no validation on startup

**Code quality**
- Dead code, unreachable branches
- Inconsistent typing (missing type hints in Python, `any` abuse in TypeScript)
- Duplicated logic that should be shared

## Process
1. First, produce a written report organized by severity (Critical / High / Medium / Low), 
   with file:line references and a one-line explanation of *why* each is a problem 
   and what could trigger it.
2. Do not fix anything yet — wait for me to review the report.
3. After I confirm, fix issues starting with Critical, then High, etc. For each fix, 
   briefly explain the change and why it's safer.
4. After fixes are applied, re-scan the changed files once more to confirm no new 
   issues were introduced.

Be skeptical of your own first pass — if a file has complex logic (parsing, protocol 
decoding, concurrency, crypto), review it twice.
